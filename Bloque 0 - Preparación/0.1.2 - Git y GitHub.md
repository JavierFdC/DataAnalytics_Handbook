## 2. El problema que resuelve Git

Todos hemos visto una carpeta así:

```
informe_ventas.xlsx
informe_ventas_v2.xlsx
informe_ventas_v2_revisado.xlsx
informe_ventas_final.xlsx
informe_ventas_final_DEFINITIVO.xlsx
informe_ventas_final_DEFINITIVO_ahora_si.xlsx
```

Es un sistema de control de versiones hecho a mano, y tiene todos los defectos posibles: no sabemos qué cambió entre una versión y otra, ni quién lo cambió, ni por qué; ocupa espacio por duplicado; y en cuanto dos personas trabajan a la vez, alguien sobrescribe el trabajo del otro.

Un **sistema de control de versiones** resuelve esto guardando un historial de "fotografías" del proyecto. Cada fotografía registra **qué** cambió, **quién** lo cambió, **cuándo** y, lo más importante, **por qué** (un mensaje que escribimos nosotros). Podemos volver a cualquier punto del historial, comparar dos versiones o trabajar en paralelo sin pisarnos.

Para un analista de datos esto significa: saber qué versión de la consulta SQL generó la cifra que se presentó al comité, poder deshacer el cambio que rompió el script de limpieza, y colaborar con otros analistas sobre el mismo proyecto.

## 3. ¿Qué es Git y qué es GitHub?

Es la confusión más habitual del principiante, así que la resolvemos antes de instalar nada.

**Git** es un **programa** que se instala en nuestro ordenador y gestiona el historial de versiones de una carpeta. Funciona completamente sin internet. Lo creó Linus Torvalds en 2005 para gestionar el desarrollo de Linux, y hoy es el estándar absoluto de la industria.

**GitHub** es una **plataforma web** (propiedad de Microsoft) que aloja repositorios de Git en la nube. Añade todo lo que Git no tiene: una interfaz web para ver el código, colaboración entre personas, pull requests, revisión de código, gestión de tareas y un perfil público que funciona como portfolio.

Git es el motor; GitHub es un servicio construido encima. Hay alternativas a GitHub (**GitLab**, **Bitbucket**, **Azure DevOps**) que usan el mismo Git por debajo. Todo lo que aprendamos hoy sirve para todas ellas.

### Git vs Google Drive, OneDrive o Dropbox

También guardan versiones y sincronizan con la nube. La diferencia es la filosofía:

| | Drive / OneDrive / Dropbox | Git + GitHub |
|---|---|---|
| Cuándo se guarda una versión | Automáticamente, en cada cambio | Cuando **nosotros** decidimos (commit) |
| Qué explica cada versión | Nada: solo la fecha | Un mensaje escrito por nosotros |
| Trabajo en paralelo | Conflictos y "copias en conflicto" | Ramas que luego se fusionan |
| Pensado para | Documentos | Código, consultas, scripts, texto |

Git brilla con archivos de **texto** (`.sql`, `.py`, `.md`, `.csv` pequeños), porque puede mostrar exactamente qué líneas cambiaron. Con archivos binarios (un `.pbix` o un `.xlsx`) solo sabe que "el archivo cambió", sin poder mostrar el detalle.

### La frase clave

> Git guarda la historia de nuestro trabajo; GitHub la comparte. Un commit es una foto con pie de foto: el pie es tan importante como la foto.

## 4. Instalación paso a paso

### Windows

Hay dos formas de instalarlo:

**Vía instalador (recomendada).** Descargamos el instalador desde `https://git-scm.com/downloads` (Git for Windows) y lo ejecutamos. El asistente tiene muchas pantallas; **aceptamos las opciones por defecto salvo dos**:

| Pantalla del instalador | Qué elegimos | Por qué |

### macOS

Si Git no está instalado, macOS ofrece instalar las **Command Line Tools de Xcode**, que lo incluyen. Aceptamos y esperamos unos minutos. Alternativa, si usamos Homebrew: `brew install git`.

### Linux


## 5. Configuración inicial

Git firma cada commit con un nombre y un email. Se configura **una sola vez** por ordenador:

```bash
git config --global user.name "Javier Fernández"
git config --global user.email "javier.fernandez@ejemplo.com"
git config --global init.defaultBranch main
```

- `user.name`: el nombre que aparecerá como autor de nuestros commits. Nombre real, que es un portfolio.
- `user.email`: **el mismo email con el que crearemos la cuenta de GitHub**, para que GitHub asocie los commits a nuestro perfil.
- `init.defaultBranch main`: la rama principal se llamará `main` (en Windows ya lo elegimos en el instalador; en macOS y Linux lo fijamos aquí).

Comprobamos la configuración:

```bash
git config --global --list
```

> **Privacidad del email.** Los commits son públicos en un repositorio público, y el email va dentro. Si no queremos exponerlo, GitHub ofrece una dirección anónima del tipo `12345678+usuario@users.noreply.github.com` en **Settings > Emails**. Podemos usarla en `user.email` una vez creada la cuenta.

## 6. Los conceptos clave

### Repositorio

Un **repositorio** (o *repo*) es una carpeta cuyo historial gestiona Git. Por fuera parece una carpeta normal; por dentro contiene una subcarpeta oculta `.git` donde Git guarda toda la historia.

### Las tres áreas de Git

Este es el concepto que más cuesta al principio y el que más problemas evita después. Git distingue tres lugares donde puede estar un cambio:

```
 Directorio de trabajo         Staging area               Repositorio
 (working directory)           (área de preparación)      (historial)
 ┌──────────────────┐          ┌──────────────────┐       ┌──────────────────┐
 │ Los archivos tal │  git add │ Los cambios que  │  git  │ Las fotos        │
 │ como los vemos y ├─────────►│ irán en la       ├──────►│ guardadas        │
 │ editamos         │          │ próxima foto     │ commit│ (commits)        │
 └──────────────────┘          └──────────────────┘       └──────────────────┘
```

1. **Directorio de trabajo.** Los archivos tal y como están ahora en la carpeta. Aquí editamos.
2. **Staging area.** Una zona intermedia donde **elegimos qué cambios** entrarán en la próxima foto. Se añaden con `git add`.
3. **Repositorio.** El historial de fotos guardadas. Se añade una foto con `git commit`.

### Analogía: la foto de grupo

Preparar un commit es como hacer una foto de grupo en una boda. El directorio de trabajo es todo el salón, con gente moviéndose. La *staging area* es el grupo que colocamos delante de la cámara: elegimos quién sale en esta foto (`git add`). El commit es el disparo: la foto queda guardada para siempre, con un pie de foto que explica qué momento era. Los que no colocamos delante siguen en el salón y pueden salir en la foto siguiente.

¿Para qué sirve la zona intermedia? Para hacer **commits con sentido**. Si hemos corregido una consulta y además hemos empezado un script nuevo a medias, podemos guardar solo la corrección en un commit ("Corregir filtro de fechas en la consulta de ventas") y dejar el script para más adelante.

### Commit

Un **commit** es una foto del proyecto en un momento dado. Cada commit tiene:

- Un **identificador único** (*hash*), como `a3f5c21`.
- **Autor** y **fecha**.
- Un **mensaje** que explica el cambio.
- Una referencia al **commit anterior** (su "padre"), lo que forma la cadena del historial.

### Cómo escribir un buen mensaje de commit

El mensaje es para la persona que lea el historial dentro de seis meses, que probablemente seremos nosotros. Tres reglas:

1. **Verbo en infinitivo y en imperativo**, describiendo qué hace el commit: "Añadir chuleta de terminal", "Corregir filtro de fechas".
2. **Breve**: la primera línea, de 50 caracteres o menos.
3. **Qué y por qué**, no cómo: el cómo ya está en el código.

| Mal mensaje | Buen mensaje |
|---|---|
| `cambios` | `Añadir consulta de ventas por región` |
| `arreglado` | `Corregir duplicados en la unión de clientes` |
| `asdfgh` | `Eliminar columnas vacías del CSV de reservas` |
| `final` | `Completar práctica 2.1.3 de JOINs` |

## 7. Primer repositorio local paso a paso

### Paso 1: situarnos en el portfolio

```bash
cd ~/proyectos/mi-portfolio-data-analytics
```

### Paso 2: inicializar el repositorio

```bash
git init
```

```
Initialized empty Git repository in C:/Users/javier/proyectos/mi-portfolio-data-analytics/.git/
```

Git ha creado la carpeta oculta `.git`. Podemos verla con `ls -Force` (Windows) o `ls -a` (macOS). **Nunca tocamos nada dentro de `.git` a mano.**

### Paso 3: consultar el estado

```bash
git status
```

```
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        README.md
        notas/

nothing added to commit but untracked files present (use "git add" to track)
```

`git status` es el comando que más usaremos: nos dice en qué rama estamos y qué ha cambiado. Ante la duda, `git status`. Los archivos aparecen como *untracked* (sin seguimiento): Git los ve, pero todavía no los vigila.

> Fijémonos en que `practicas/` no aparece. Git **no rastrea carpetas vacías**, solo archivos. Cuando tenga contenido, aparecerá.

### Paso 4: preparar los cambios

```bash
git add README.md notas/terminal.md
git status
```

Ahora los archivos aparecen en verde bajo *Changes to be committed*: están en la *staging area*. Para añadir todo lo que ha cambiado en la carpeta actual existe el atajo `git add .` (el punto es "la carpeta actual", como vimos en la sesión 1).

### Paso 5: el primer commit

```bash
git commit -m "Crear estructura inicial del portfolio"
```

```
[main (root-commit) a3f5c21] Crear estructura inicial del portfolio
 2 files changed, 12 insertions(+)
 create mode 100644 README.md
 create mode 100644 notas/terminal.md
```

La opción `-m` permite escribir el mensaje directamente. Si la olvidamos, Git abre el editor configurado para que escribamos el mensaje allí.

### Paso 6: ver el historial

```bash
git log --oneline
```

```
a3f5c21 (HEAD -> main) Crear estructura inicial del portfolio
```

Ya tenemos historia. Para probar el ciclo completo, abrimos `notas/terminal.md` con el editor, añadimos los comandos de Git que acabamos de aprender, guardamos y repetimos:

```bash
git status
git add notas/terminal.md
git commit -m "Añadir comandos básicos de Git a la chuleta"
git log --oneline
```

Dos commits. El ciclo **editar → `git add` → `git commit`** es el latido de Git: lo repetiremos cientos de veces durante el curso.

## 8. Publicar en GitHub

### Paso 1: crear la cuenta

Vamos a `https://github.com` y nos registramos. Dos consejos:

- **El nombre de usuario será público y aparecerá en la URL de nuestro portfolio** (`github.com/usuario`). Algo profesional: nombre y apellido, sin números aleatorios.
- Activamos la **autenticación en dos pasos** (*two-factor authentication*) cuando GitHub lo pida. Es obligatoria para publicar código.

### Paso 2: crear el repositorio remoto

En GitHub, botón **New** (o el `+` de arriba a la derecha → **New repository**):

- **Repository name:** `mi-portfolio-data-analytics` (el mismo nombre que la carpeta local).
- **Description:** "Portfolio de prácticas del curso de Data Analytics".
- **Public.**
- **No marcamos** *Add a README file*, ni *.gitignore*, ni licencia. Ya tenemos contenido en local; si GitHub crea archivos por su cuenta, los dos historiales empezarían distintos y habría que reconciliarlos.

Pulsamos **Create repository**. GitHub nos muestra una página con instrucciones; nos interesa la sección *…or push an existing repository from the command line*.

### Paso 3: conectar el repositorio local con el remoto

```bash
git remote add origin https://github.com/<usuario>/mi-portfolio-data-analytics.git
```

Esto le dice a nuestro Git local: "existe una copia remota en esta URL y la vamos a llamar `origin`". `origin` es el nombre convencional del remoto principal.

### Paso 4: subir el historial

```bash
git push -u origin main
```

La primera vez nos pedirá autenticarnos:

- **Windows:** Git Credential Manager abre una ventana; elegimos **Sign in with your browser**, autorizamos en GitHub y listo. Las credenciales quedan guardadas.
- **macOS y Linux:** la forma más sencilla es instalar GitHub CLI (`brew install gh` en macOS) y ejecutar `gh auth login` una vez, eligiendo *GitHub.com* → *HTTPS* → *Login with a web browser* y aceptando autenticar Git con esas credenciales.

> **GitHub no acepta la contraseña de la cuenta desde la terminal** desde 2021. Si la terminal nos pide usuario y contraseña a pelo, algo no está bien configurado: revisamos el paso anterior.

La opción `-u` vincula nuestra rama `main` local con la remota; a partir de ahora bastará con escribir `git push`.

### Paso 5: comprobarlo en la web

Recargamos la página del repositorio en GitHub. Veremos nuestros archivos, el número de commits y el mensaje del último. Clic en el contador de commits: ahí está nuestro historial, con nuestros mensajes.

## 9. Ramas y pull requests

Hasta ahora hemos trabajado directamente sobre `main`. En proyectos reales eso no se hace: `main` es la versión "buena", la que funciona. Los cambios se preparan aparte y solo se incorporan a `main` cuando están revisados.

### Qué es una rama

Una **rama** (*branch*) es una línea de trabajo paralela. Creamos una rama, hacemos commits en ella sin afectar a `main`, y cuando el trabajo está listo lo **fusionamos** (*merge*) de vuelta.

```
main:    A ─── B ──────────────── M
                \                /
rama:            C ───── D ─────
```

`A` y `B` son los commits en `main`. Creamos la rama, hacemos `C` y `D`, y al fusionar aparece `M` en `main` con todo el trabajo incorporado.

### Qué es un pull request

Un **pull request** (PR) es una **petición en GitHub** para fusionar una rama en otra: "he terminado este trabajo en mi rama, por favor, revisadlo e incorporadlo a `main`". Es el centro de la colaboración: permite ver los cambios línea a línea, comentarlos, pedir correcciones y dejar constancia de por qué se hizo cada cosa. Es una característica de GitHub, no de Git.

En este curso usaremos este flujo incluso trabajando solos, porque es **exactamente como se trabaja en un equipo de datos**, y porque cada PR bien descrito es una pieza más de nuestro portfolio.

### Paso 1: crear una rama

Vamos a añadir un archivo `.gitignore` en una rama propia:

```bash
git switch -c anadir-gitignore
```

`switch -c` crea la rama y nos cambia a ella. (En tutoriales antiguos veremos `git checkout -b`, que hace lo mismo.) El prompt o `git status` confirman que ya no estamos en `main`:

```bash
git status
```

```
On branch anadir-gitignore
nothing to commit, working tree clean
```

> Los nombres de rama siguen la misma convención que los archivos: minúsculas, guiones y sin tildes ni `ñ`.

### Paso 2: crear el `.gitignore`

El archivo **`.gitignore`** le dice a Git qué archivos **no debe vigilar nunca**. En un proyecto de datos es fundamental: evita subir a GitHub archivos generados automáticamente, entornos de Python con miles de archivos, y sobre todo, **credenciales y datos sensibles**.

```powershell
notepad .gitignore        # Windows
```

```bash
touch .gitignore && open -e .gitignore        # macOS
```

Escribimos este contenido y guardamos:

```
# Entornos virtuales de Python (sesión 0.1.5)
.venv/

# Archivos temporales de Python y Jupyter
__pycache__/
.ipynb_checkpoints/

# Credenciales y variables de entorno: NUNCA a GitHub
.env

# Archivos del sistema operativo
.DS_Store
Thumbs.db
desktop.ini
```

Las líneas que empiezan por `#` son comentarios. Una línea terminada en `/` ignora esa carpeta entera.

### Paso 3: commit y push de la rama

```bash
git add .gitignore
git commit -m "Añadir .gitignore para Python y archivos del sistema"
git push -u origin anadir-gitignore
```

### Paso 4: abrir el pull request

Volvemos a GitHub. Aparecerá un aviso amarillo: *anadir-gitignore had recent pushes* con el botón **Compare & pull request**. Lo pulsamos.

- **Base:** `main` ← **compare:** `anadir-gitignore`. Es decir, queremos llevar los cambios de la rama a `main`.
- **Título:** GitHub propone el mensaje del commit; nos vale.
- **Descripción:** explicamos brevemente qué hace el cambio y por qué. Por ejemplo: "Añade un .gitignore para no subir entornos virtuales, checkpoints de Jupyter ni credenciales".

Pulsamos **Create pull request**.

### Paso 5: revisar y fusionar

Dentro del PR, la pestaña **Files changed** muestra los cambios línea a línea: en verde lo añadido, en rojo lo eliminado. Es lo que haría un compañero al revisar nuestro trabajo. Lo revisamos nosotros mismos.

Volvemos a la pestaña **Conversation** y pulsamos **Merge pull request** → **Confirm merge**. GitHub ofrece después **Delete branch**: la borramos, ya no la necesitamos.

### Paso 6: actualizar nuestro repositorio local

La fusión ha ocurrido **en GitHub**. Nuestro `main` local todavía no lo sabe:

```bash
git switch main
git pull
git branch -d anadir-gitignore
git log --oneline
```

- `git switch main`: volvemos a la rama principal.
- `git pull`: descarga los cambios del remoto y los incorpora. Ahora el `.gitignore` también está en nuestro `main` local.
- `git branch -d`: borra la rama local, que ya está fusionada.

## 10. El ciclo de trabajo diario

Resumiendo todo lo anterior, este es el flujo que seguiremos durante el curso para cada práctica:

```bash
git switch main
git pull                                  # 1. partir de la última versión
git switch -c practica-2-1-3              # 2. rama para el trabajo nuevo
# ... trabajamos, editamos archivos ...
git status                                # 3. qué ha cambiado
git add .                                 # 4. preparar
git commit -m "Completar práctica 2.1.3"  # 5. guardar la foto
git push -u origin practica-2-1-3         # 6. subir la rama
# 7. abrir el pull request en GitHub, revisar y fusionar
# 8. volver a main y hacer git pull
```

Los siete comandos que acabamos de usar (`init`, `status`, `add`, `commit`, `push`, `pull`, `switch`) son el 90 % del Git que necesita un analista.

## 11. Lo que Git ha hecho por debajo

Toda la magia vive en la carpeta oculta `.git`. Podemos asomarnos, sin tocar nada:

```bash
cat .git/HEAD
```

```
ref: refs/heads/main
```

`HEAD` es un puntero que indica **en qué rama estamos**. Y una rama no es más que un archivo pequeño que contiene el hash del último commit de esa rama:

```bash
cat .git/refs/heads/main
```

```
e7d1b90c4a...
```

Por eso crear una rama en Git es instantáneo: no copia ningún archivo, solo crea un puntero nuevo de 41 bytes. Y cada commit guarda una referencia a su padre, de modo que el historial es una cadena que Git recorre hacia atrás.

Una forma visual de ver esta estructura:

```bash
git log --oneline --graph --all
```

```
*   e7d1b90 (HEAD -> main, origin/main) Merge pull request #1 from javier/anadir-gitignore
|\
| * 5b2c8e1 Añadir .gitignore para Python y archivos del sistema
|/
* 9d4a0f3 Añadir comandos básicos de Git a la chuleta
* a3f5c21 Crear estructura inicial del portfolio
```

Es exactamente el diagrama de ramas de la sección 9, dibujado por Git con nuestros propios commits.

Tres ideas que conviene retener:

- **Git guarda fotos completas, no diferencias.** Cada commit es una instantánea de todo el proyecto (comprimida y sin duplicar los archivos que no cambian).
- **Casi todo ocurre en local.** `add`, `commit`, `log`, `switch` funcionan sin internet. Solo `push` y `pull` hablan con GitHub.
- **`origin/main` es la última foto que conocemos del remoto**, no el remoto en tiempo real. Por eso hay que hacer `git pull` para enterarse de los cambios hechos en GitHub.

## 12. Errores comunes y troubleshooting

**1. "git no se reconoce como comando."** Acabamos de instalar Git y la terminal estaba abierta de antes. Cerramos la terminal y abrimos una nueva. Si persiste, reinstalamos asegurándonos de que la opción de PATH es la recomendada.

**2. "Author identity unknown. Please tell me who you are."** No hemos configurado `user.name` y `user.email`. Repetimos la sección 5.

**3. "fatal: not a git repository."** Estamos ejecutando un comando de Git fuera del repositorio. `pwd` para ver dónde estamos y `cd ~/proyectos/mi-portfolio-data-analytics`.

**4. "error: src refspec main does not match any."** Intentamos hacer `push` de una rama que no existe o que todavía no tiene commits. Comprobamos con `git status` que hemos hecho al menos un commit y con `git branch` cómo se llama nuestra rama: si se llama `master`, la renombramos con `git branch -m master main`.

**5. "! [rejected] main -> main (fetch first)."** El remoto tiene commits que nosotros no tenemos (por ejemplo, porque fusionamos un PR en GitHub y no hicimos `pull`, o porque creamos el repositorio remoto con README). Hacemos `git pull` y después `git push`.

**6. "He hecho commits en `main` en lugar de en una rama."** No pasa nada grave en un repositorio personal. Si todavía no hemos hecho `push`, podemos crear la rama desde ese punto (`git switch -c nombre-rama`), que se lleva los commits, y seguir el flujo de PR. Si ya los subimos a `main`, los dejamos así y en el próximo trabajo empezamos por la rama.

**7. "Support for password authentication was removed."** Hemos introducido la contraseña de GitHub en la terminal. GitHub no la acepta: hay que autenticarse con el navegador mediante Git Credential Manager (Windows) o `gh auth login` (macOS/Linux).

**8. "warning: in the working copy of 'README.md', LF will be replaced by CRLF."** Es un aviso, no un error. Windows y Unix marcan el final de línea de forma distinta, y Git lo normaliza automáticamente. Podemos ignorarlo.

**9. "Git me ha abierto una pantalla rara y no sé salir."** Hemos hecho `git commit` sin `-m` y el editor es Vim. Para salir guardando: pulsamos `Esc`, escribimos `:wq` y Enter. Para salir sin guardar: `Esc`, `:q!` y Enter. En la sesión 3 configuraremos VS Code como editor para que no vuelva a pasar.

## 14. Para profundizar

### Ver y deshacer cambios

```bash
git diff                       # qué ha cambiado y no está en staging
git diff --staged              # qué está en staging y entrará en el commit
git restore archivo.sql        # descartar cambios no guardados de un archivo
git restore --staged archivo   # sacar un archivo de staging sin perder los cambios
git revert <hash>              # crear un commit que deshace otro commit
```

`git revert` es la forma segura de deshacer un commit ya publicado: no borra historia, añade un commit que invierte el cambio. Existe también `git reset`, más potente y más peligroso, que reescribe el historial; conviene no usarlo sobre commits ya subidos a GitHub.

### Conflictos de fusión

Si dos ramas modifican **las mismas líneas** del mismo archivo, Git no sabe cuál elegir y marca un **conflicto**:

```
<<<<<<< HEAD
WHERE fecha >= '2024-01-01'
=======
WHERE fecha >= '2023-01-01'
>>>>>>> otra-rama
```

Se resuelve editando el archivo para dejar la versión correcta, borrando las marcas, y haciendo `add` y `commit`. VS Code tiene un editor visual de conflictos que lo facilita mucho (sesión 3).

### Patrones de `.gitignore`

```
*.log              # todos los archivos .log
data/raw/          # una carpeta concreta
!data/raw/.gitkeep # excepción: sí incluir este archivo
*.pbix             # binarios pesados que no queremos versionar
```

GitHub mantiene una colección de plantillas en <https://github.com/github/gitignore>.

### Datos en Git: sí y no

Git no está pensado para archivos grandes. Buenas prácticas en proyectos de datos: los CSV pequeños de ejemplo se pueden versionar; los datasets grandes, no (se descargan con un script o se versionan con herramientas específicas como Git LFS o DVC). Y **nunca, jamás**, credenciales, contraseñas o datos personales: una vez en el historial de un repositorio público, hay que darlos por comprometidos aunque se borren después.

### Otros conceptos que aparecerán en el mundo real

- **Fork:** copia de un repositorio ajeno en nuestra cuenta, para proponer cambios mediante PR. Es como se contribuye a proyectos open source.
- **Clone:** `git clone <url>` descarga un repositorio existente con todo su historial. Es lo que haremos para descargar el material del curso.
- **SSH:** alternativa a HTTPS para autenticarse con claves en lugar de navegador.
- **Conventional Commits:** convención de mensajes con prefijos (`feat:`, `fix:`, `docs:`) usada en muchos equipos.
- **GitHub Actions:** automatizaciones que se ejecutan en GitHub con cada push (tests, validaciones, despliegues).
