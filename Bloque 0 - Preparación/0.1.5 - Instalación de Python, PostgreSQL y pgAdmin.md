## 3. ¿Qué es y qué no un entorno virtual?

### El problema

Imaginemos que en el bloque 3 hacemos un análisis con pandas 2.2. Meses después, para el proyecto final, instalamos pandas 3.0, que cambia el comportamiento de algunas funciones. Si solo hay **una** instalación de Python en el ordenador, al actualizar pandas para un proyecto **rompemos el otro**. Y si un compañero quiere ejecutar nuestro análisis, no sabe qué versiones exactas necesita.

### La solución

Un **entorno virtual** es una carpeta dentro del proyecto (la llamaremos `.venv`) que contiene **su propia copia de Python y sus propias librerías**, independiente del resto del sistema. Cada proyecto tiene la suya. Lo que instalamos en un entorno no afecta a ningún otro.

Junto al entorno, un archivo **`requirements.txt`** enumera las librerías que necesita el proyecto. Con él, cualquiera puede recrear el entorno con un solo comando.

### Analogía

Python instalado en el sistema es la cocina de casa. Un entorno virtual es una **fiambrera preparada para una receta concreta**: lleva exactamente los ingredientes que esa receta necesita, en las cantidades justas. Si una receta pide sal gorda y otra sal fina, cada fiambrera lleva la suya y no hay conflicto. Y `requirements.txt` es la lista de la compra: con ella cualquiera puede preparar la misma fiambrera.

### Lo que no es

- **No es una máquina virtual.** No emula otro ordenador ni otro sistema operativo; es solo una carpeta con Python y librerías.
- **No se sube a GitHub.** Pesa cientos de megas y depende del sistema operativo. Se sube `requirements.txt`, y cada uno recrea el entorno. Por eso en la sesión 2 pusimos `.venv/` en el `.gitignore`.

### La frase clave

> Un proyecto, un entorno virtual. Nunca instalamos librerías en el Python del sistema: lo que no está en `requirements.txt` no existe.

## 4. Instalación de Python

En el curso usaremos **Python 3.13**. Cualquier versión 3.12 o superior sirve; lo importante es que todos usemos una versión moderna para evitar diferencias.

### Windows

**Vía instalador de python.org (recomendada).** Vamos a `https://www.python.org/downloads/` y descargamos el instalador de Windows de la versión 3.13.

En la primera pantalla del instalador hay una casilla que decide si todo lo demás funcionará:

- **Marcamos "Add python.exe to PATH"**, abajo del todo. Sin ella, la terminal no encontrará Python (sesión 1, sección 8).
- Pulsamos **Install Now**.
- Si al final aparece la opción **Disable path length limit**, la pulsamos: evita errores con rutas largas al instalar algunas librerías.

> python.org está sustituyendo progresivamente el instalador clásico de Windows por el **Python install manager**, una herramienta que gestiona varias versiones con el comando `py`. Si la página de descargas nos ofrece esa opción, podemos seguirla: el resultado para el curso es el mismo, siempre que al final `python --version` responda en la terminal.

**Un problema muy frecuente en Windows: los alias de la Microsoft Store.** Windows trae unos "atajos" llamados `python.exe` que, en lugar de ejecutar Python, **abren la Microsoft Store**. Si al escribir `python` se abre la tienda, o aparece un mensaje diciendo que Python no se encuentra y sugiriendo la Store:

1. **Configuración > Aplicaciones > Configuración avanzada de aplicaciones > Alias de ejecución de aplicaciones.**
2. Desactivamos los dos interruptores de **Instalador de aplicación: python.exe** y **python3.exe**.
3. Abrimos una terminal nueva.

### macOS

macOS puede traer un Python antiguo del sistema que **no debemos usar ni modificar**. Instalamos uno propio:

- **Vía python.org:** descargamos el instalador `.pkg` para macOS de la versión 3.13 y seguimos el asistente. Al terminar, en la carpeta **Aplicaciones > Python 3.13** ejecutamos **Install Certificates.command** (evita errores de conexión segura al descargar datos).
- **Vía Homebrew**, si lo usamos: `brew install python@3.13`.

En macOS el comando es **`python3`**, no `python`. En el resto de la guía, donde pone `python`, en macOS escribimos `python3` (solo hasta activar el entorno virtual; dentro de él, `python` funciona en todos los sistemas).

### Linux

```bash
sudo apt install python3 python3-venv python3-pip      # Debian / Ubuntu
```

### Verificación

Terminal **nueva**:

```powershell
python --version                  # Windows
where.exe python                  # ¿qué python se está ejecutando?
```

```bash
python3 --version                 # macOS / Linux
which python3
```

```
Python 3.13.7
```

El número exacto de la última cifra no importa. Lo que sí importa es que `where.exe` / `which` muestre una ruta de nuestra instalación (en Windows, algo como `C:\Users\javier\AppData\Local\Programs\Python\Python313\python.exe`) y no una ruta de `WindowsApps`, que sería el alias de la Store.

## 6. Instalación de PostgreSQL y pgAdmin

### Windows y macOS

Usamos el instalador oficial de **EDB**, que incluye PostgreSQL y pgAdmin 4 en un solo paso. Desde `https://www.postgresql.org/download/` elegimos nuestro sistema y seguimos el enlace a los instaladores de EDB. Descargamos **la versión más reciente**.

El asistente pregunta varias cosas. Las respuestas:

| Pantalla | Qué elegimos |
|---|---|
| **Installation Directory** | La propuesta por defecto. |
| **Select Components** | Marcados: *PostgreSQL Server*, *pgAdmin 4* y *Command Line Tools*. **Desmarcamos *Stack Builder***: no lo necesitamos. |
| **Data Directory** | La propuesta por defecto. Es donde vivirán físicamente las bases de datos. |
| **Password** | La contraseña del superusuario `postgres`. **La apuntamos en un sitio seguro**: la pediremos constantemente y no se puede recuperar fácilmente. |
| **Port** | `5432`, el puerto estándar de PostgreSQL. No lo cambiamos. |
| **Advanced Options (Locale)** | *Default locale*. |

Al terminar, si pregunta por lanzar Stack Builder, desmarcamos la casilla y pulsamos **Finish**.

> Para usar PostgreSQL de forma local la contraseña puede ser sencilla, pero **nunca** la reutilizamos de otra cuenta y **nunca** la escribimos dentro de un archivo que vaya a GitHub.

En macOS, una alternativa muy popular es **Postgres.app** (`https://postgresapp.com/`), que se instala arrastrando a Aplicaciones. En ese caso, pgAdmin se descarga aparte desde `https://www.pgadmin.org/download/`.

### Linux

```bash
sudo apt install postgresql
sudo -u postgres psql -c "ALTER USER postgres PASSWORD 'nuestra_contraseña';"
```

pgAdmin se instala desde su repositorio oficial, siguiendo las instrucciones de `https://www.pgadmin.org/download/`.

### Comprobar que el servidor está en marcha

PostgreSQL se instala como un **servicio** que arranca con el ordenador. En Windows, podemos verlo en la aplicación **Servicios** (tecla Windows, escribir `servicios`): aparece como `postgresql-x64-<versión>` con estado *En ejecución*. No hay que abrir nada para que funcione: está siempre escuchando en el puerto 5432.

## 8. Verificación final: Python habla con PostgreSQL

Es el momento de comprobar que las dos piezas se entienden. En `practicas/bloque-00/` creamos `verificar_entorno.py`:

```python
"""Verificación del entorno del curso: Python, librerías y conexión a PostgreSQL."""

import getpass
import sys

import matplotlib
import numpy
import pandas
import psycopg
import seaborn
import sklearn
import sqlalchemy

print(f"Python        {sys.version.split()[0]}")
print(f"Ejecutable    {sys.executable}")
print()

for libreria in (numpy, pandas, matplotlib, seaborn, sklearn, sqlalchemy, psycopg):
    print(f"{libreria.__name__:<14}{libreria.__version__}")
print()

contrasena = getpass.getpass("Contraseña del usuario postgres: ")

with psycopg.connect(
    host="localhost",
    port=5432,
    dbname="curso_data_analytics",
    user="postgres",
    password=contrasena,
) as conexion:
    version = conexion.execute("SELECT version();").fetchone()[0]
    filas = conexion.execute("SELECT mensaje FROM prueba_entorno;").fetchall()

print(f"PostgreSQL    {version}")
print(f"prueba_entorno: {len(filas)} fila(s) -> {filas[0][0]}")
print()
print("Entorno listo para el curso.")
```

3. **Pide la contraseña** de `postgres` sin mostrarla en pantalla (`getpass`). Nunca la escribimos en el código: el archivo irá a GitHub.
4. **Se conecta a PostgreSQL**, pregunta la versión y lee la tabla que creamos con pgAdmin.

## 9. Lo que ha pasado por debajo

### El entorno virtual es solo una carpeta y un cambio de PATH

Si miramos dentro de `.venv` encontramos:

```
.venv/
├── pyvenv.cfg          ← qué Python del sistema se usó para crearlo
├── Scripts/            ← Windows (en macOS/Linux: bin/)
│   ├── python.exe
│   ├── pip.exe
│   └── Activate.ps1
└── Lib/site-packages/  ← aquí se instalan las librerías (macOS/Linux: lib/python3.13/site-packages/)
```

Y **activar** el entorno no hace nada mágico: el script de activación **pone la carpeta `.venv/Scripts` al principio del PATH** de esa terminal. Cuando escribimos `python`, la terminal busca en el PATH por orden (sesión 1, sección 8) y encuentra primero el del entorno. Por eso `where.exe python` mostraba la ruta de `.venv` en primer lugar. `deactivate` restaura el PATH original.

### pip descarga de PyPI

`pip install pandas` consulta **PyPI** (*Python Package Index*, `https://pypi.org`), el repositorio público de paquetes de Python, descarga el paquete ya preparado para nuestro sistema (un archivo *wheel*, `.whl`) y lo descomprime en `site-packages`. Si pandas necesita NumPy, pip lo detecta y lo instala también: son las **dependencias**.

### Cliente y servidor hablan por red, aunque estén en el mismo equipo

Cuando Python se conecta con `host="localhost", port=5432`, abre una conexión de red **hacia nuestro propio ordenador** (`localhost`), al puerto donde escucha PostgreSQL. pgAdmin hace exactamente lo mismo. Si mañana la base de datos estuviera en un servidor en la nube, el código sería idéntico salvo por el `host`. Y los datos no viven en nuestro repositorio ni en la carpeta del proyecto: viven en el *Data Directory* de PostgreSQL, gestionados por el servidor.

## 10. Errores comunes y troubleshooting

**1. "Al escribir `python` se abre la Microsoft Store" o "Python no se encontró".** Son los alias de ejecución de Windows. Los desactivamos (sección 4) y abrimos una terminal nueva. Si aun así no funciona, reinstalamos Python marcando **Add python.exe to PATH**.

**2. "La ejecución de scripts está deshabilitada en este sistema" al activar el entorno.** Política de ejecución de PowerShell. `Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser` y volvemos a activar.

**3. "ModuleNotFoundError: No module named 'pandas'" aunque lo hemos instalado.** Estamos ejecutando un Python distinto del que tiene la librería. Comprobamos que el prompt muestra `(.venv)` y que `where.exe python` / `which python` apunta a `.venv`. En VS Code, revisamos que **Python: Select Interpreter** apunta a `.venv`.

**4. "pip install falla con un error largo en rojo."** Leemos las últimas líneas: suelen decir el motivo. Causas habituales: sin conexión o con un proxy corporativo (probamos desde otra red), o una versión de Python demasiado nueva para la que la librería todavía no tiene paquetes publicados (instalamos la versión recomendada, 3.13).

**5. "`psql` no se reconoce como comando."** El instalador de Windows no añade las herramientas de PostgreSQL al PATH. No es necesario para el curso (usaremos pgAdmin y Python). Si queremos `psql` en la terminal, añadimos al PATH la carpeta `C:\Program Files\PostgreSQL\<versión>\bin`.

**6. "password authentication failed for user postgres."** La contraseña no es la de la instalación. Cuidado con el bloqueo de mayúsculas y la distribución del teclado. Si la hemos olvidado de verdad, en una instalación recién hecha lo más rápido es desinstalar PostgreSQL, borrar la carpeta de datos y reinstalar.

**7. "connection refused" / "could not connect to server" desde Python o pgAdmin.** El servidor no está en marcha. En Windows, en **Servicios**, buscamos `postgresql-x64-<versión>` y pulsamos **Iniciar**. Comprobamos también que el puerto es 5432.

**8. "El instalador de PostgreSQL dice que el puerto 5432 está en uso."** Ya hay otro PostgreSQL instalado (quizá de un curso anterior). Podemos usar ese, si recordamos su contraseña, o desinstalarlo antes de continuar.

**9. "relation prueba_entorno does not exist" al ejecutar el script.** La tabla se creó en otra base de datos (probablemente en `postgres`). En pgAdmin, comprobamos que el Query Tool estaba abierto sobre `curso_data_analytics` (su nombre aparece en la pestaña) y repetimos el paso 5 de la sección 7.

**10. "`git status` muestra miles de archivos dentro de `.venv`."** El `.gitignore` no existe, no está en la raíz del proyecto o no contiene `.venv/`. Lo revisamos (sesión 2, sección 9) **antes** de hacer commit.

## 12. Para profundizar

### Fijar versiones exactas

Nuestro `requirements.txt` pide "la última versión" de cada librería, que es lo razonable al empezar un curso. En un proyecto profesional se fijan versiones para que el entorno sea **reproducible** dentro de un año:

```bash
pip freeze > requirements-lock.txt
```

`pip freeze` lista cada paquete instalado con su versión exacta (`pandas==2.3.2`). Con ese archivo, cualquiera recrea exactamente el mismo entorno.

### Alternativas modernas: uv y conda

- **uv:** un gestor de paquetes y entornos para Python muy rápido (hasta decenas de veces más que pip), cada vez más adoptado en la industria. `uv venv` y `uv pip install -r requirements.txt` sustituyen a los comandos de esta sesión.
- **conda / Anaconda / Miniconda:** muy popular en ciencia de datos, gestiona también versiones de Python y librerías no escritas en Python. Es otra filosofía (entornos centralizados, no dentro del proyecto); no la usaremos en el curso para no mezclar sistemas.

### `psql`, el cliente de terminal

Todo lo que hemos hecho con pgAdmin se puede hacer desde la terminal con `psql`:

```bash
psql -U postgres -d curso_data_analytics
```

Dentro, además de SQL, hay comandos propios que empiezan por barra invertida: `\l` lista las bases de datos, `\dt` las tablas, `\d prueba_entorno` describe una tabla, y `\q` sale.

### Credenciales fuera del código: archivos `.env`

Pedir la contraseña con `getpass` sirve para un script de verificación, pero no para un proceso automático. La práctica profesional es guardarla en un archivo `.env` (que ya está en nuestro `.gitignore`) y leerla con la librería `python-dotenv`:

```
# .env — NUNCA se sube a GitHub
PGPASSWORD=mi_contraseña
```

```python
import os
from dotenv import load_dotenv

load_dotenv()
contrasena = os.environ["PGPASSWORD"]
```

### PostgreSQL con Docker

En equipos profesionales es habitual no instalar PostgreSQL en el ordenador sino ejecutarlo en un **contenedor Docker**, que se crea y se destruye con un comando y garantiza la misma versión para todo el equipo. Es un tema propio de ingeniería de datos que se sale del alcance del curso.

### Otros clientes de bases de datos

Además de pgAdmin: **DBeaver** (gratuito, se conecta a casi cualquier base de datos), **DataGrip** (de pago, de JetBrains) o la extensión **SQLTools** de VS Code que instalamos en la sesión 3. Para configurar esta última: icono de SQLTools en la barra de actividad → **Add New Connection** → PostgreSQL, con los mismos datos que usa el script.
