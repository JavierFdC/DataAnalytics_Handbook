## 2. ¿Qué es y qué no VS Code?

**VS Code es un editor de código**: un programa para escribir texto que, además, entiende lo que escribimos. Colorea la sintaxis, sugiere nombres mientras tecleamos, detecta errores antes de ejecutar y se integra con la terminal y Git. Es gratuito, funciona en Windows, macOS y Linux, lo desarrolla Microsoft y es, con diferencia, el editor más usado del mundo según las encuestas anuales de Stack Overflow.

Su gran característica es que **viene casi vacío y se amplía con extensiones**. VS Code recién instalado no sabe ejecutar Python ni conectar con PostgreSQL. Cada capacidad se añade con una extensión, lo que lo hace ligero y adaptable a cualquier lenguaje.

### Comparación con lo que ya conocemos (y con lo que oiremos)

**VS Code vs bloc de notas.** Los dos editan texto plano. El bloc de notas no sabe nada del contenido; VS Code entiende SQL, Python, Markdown, JSON o CSV, y nos ayuda con cada uno.

**VS Code vs Visual Studio.** Nombres casi iguales, productos distintos. **Visual Studio** es un IDE pesado de Microsoft orientado a desarrollo de aplicaciones en C# y C++. No lo necesitamos. Si al buscar en internet aparece "Visual Studio 2022", no es lo nuestro.

**VS Code vs IDE (PyCharm, DataGrip).** Un IDE (*Integrated Development Environment*) viene con todo integrado para un lenguaje concreto. VS Code, con extensiones, se acerca mucho a un IDE, pero sirve para todos los lenguajes del curso con una sola herramienta.

**VS Code vs Jupyter.** Jupyter es el entorno de notebooks de Python, que veremos en el bloque 3. VS Code **abre y ejecuta notebooks de Jupyter** con su extensión, así que no necesitamos otra aplicación.

**VS Code vs pgAdmin.** pgAdmin es la herramienta de administración de PostgreSQL (sesión 5). En el bloque 2 usaremos pgAdmin como herramienta principal de SQL; VS Code puede también ejecutar SQL con una extensión, y lo dejaremos preparado.

### La frase clave

> VS Code no es un programa para programadores: es el sitio donde vive todo el texto del proyecto. SQL, Python, Markdown, configuración y Git, en una sola ventana.

## 3. Instalación paso a paso

### Windows

**Vía instalador (recomendada).** Descargamos desde `https://code.visualstudio.com/` el **User Installer** (el botón principal de descarga). Durante la instalación, en la pantalla *Select Additional Tasks*, marcamos:

| Opción | Marcar | Por qué |
|---|---|---|
| *Add "Open with Code" action to Windows Explorer file context menu* | Sí | Clic derecho sobre un archivo → abrir en VS Code |
| *Add "Open with Code" action to Windows Explorer directory context menu* | Sí | Clic derecho sobre una carpeta → abrir en VS Code |
| *Register Code as an editor for supported file types* | Sí | Abre `.sql`, `.py`, `.md` con VS Code por defecto |
| *Add to PATH* | **Sí, imprescindible** | Permite lanzar VS Code desde la terminal con `code` |

**Vía winget:**

```powershell
winget install --id Microsoft.VisualStudioCode -e
```

### macOS

Descargamos el `.zip` desde `https://code.visualstudio.com/`, lo descomprimimos y **arrastramos Visual Studio Code a la carpeta Aplicaciones**. Después, para poder usar el comando `code` desde la terminal:

1. Abrimos VS Code.
2. Abrimos la paleta de comandos con `Cmd + Shift + P`.
3. Escribimos `shell command` y elegimos **Shell Command: Install 'code' command in PATH**.

### Linux

Los paquetes `.deb` y `.rpm` están en la misma web. En Ubuntu también: `sudo snap install code --classic`.

### Primer arranque desde la terminal

Cerramos cualquier terminal abierta (regla de oro del PATH), abrimos una nueva y comprobamos:

```bash
code --version
```

Ahora el gesto que usaremos a diario: **abrir la carpeta del proyecto desde la terminal**.

```bash
cd ~/proyectos/mi-portfolio-data-analytics
code .
```

El punto es "la carpeta actual" (sesión 1). VS Code se abre con nuestro portfolio cargado.

La primera vez aparecerá un aviso: **Do you trust the authors of the files in this folder?** Es la función *Workspace Trust*: VS Code no ejecuta nada de una carpeta hasta que le decimos que es de confianza. Como es nuestro propio repositorio, pulsamos **Yes, I trust the authors**. Con carpetas descargadas de internet de origen desconocido, conviene pensárselo.

> **Carpeta, no archivo.** VS Code funciona mejor cuando se abre una **carpeta** (el proyecto entero) en lugar de un archivo suelto. Con la carpeta abierta, el explorador, la búsqueda y Git funcionan sobre todo el proyecto. Con un archivo suelto, nada de eso está disponible.

## 4. Recorrido por la interfaz

VS Code tiene cinco zonas. Conviene conocer sus nombres porque son los que aparecen en la documentación y en los mensajes de error.

**Barra de actividad (*Activity Bar*)** — la columna de iconos del borde izquierdo. Cada icono abre una vista en la barra lateral:

| Icono | Vista | Para qué |
|---|---|---|
| Dos hojas | **Explorer** | Árbol de archivos y carpetas del proyecto |
| Lupa | **Search** | Buscar y reemplazar en todos los archivos |
| Ramas | **Source Control** | Git: cambios, commits, ramas |
| Triángulo con bicho | **Run and Debug** | Ejecutar y depurar código |
| Cuatro cuadrados | **Extensions** | Buscar e instalar extensiones |

**Barra lateral (*Side Bar*)** — el panel que muestra la vista elegida en la barra de actividad. Se oculta y muestra con `Ctrl + B`.

**Editor** — la zona central donde editamos. Cada archivo abierto es una pestaña. Se puede dividir en varios grupos para ver dos archivos a la vez (arrastrando una pestaña a un lado).

**Panel** — la zona inferior. Contiene la **terminal integrada** y otras pestañas: *Problems* (errores detectados), *Output* (mensajes de las extensiones) y *Debug Console*.

**Barra de estado (*Status Bar*)** — la franja inferior. A la izquierda, **la rama de Git** en la que estamos y el estado de sincronización; a la derecha, el lenguaje del archivo, la codificación (`UTF-8`), el tipo de final de línea (`LF`/`CRLF`) y, cuando trabajemos con Python, el intérprete activo.

### La terminal integrada

Abrimos el panel con **View > Terminal**, o con el atajo `Ctrl + ñ` (teclado español) / `` Ctrl + ` `` (teclado inglés); en macOS, `Ctrl + ñ` o `` Ctrl + ` `` igualmente. Es **la misma terminal** que usamos en la sesión 1 (PowerShell en Windows, zsh en macOS), con una ventaja: se abre ya situada en la carpeta del proyecto. A partir de ahora, casi siempre usaremos esta.

## 5. La paleta de comandos y los atajos esenciales

### La paleta de comandos

Si solo recordamos un atajo de VS Code, que sea este: **`Ctrl + Shift + P`** (`Cmd + Shift + P` en macOS) abre la **paleta de comandos** (*Command Palette*), un buscador de **todas** las acciones de VS Code y de sus extensiones.

¿No recordamos dónde está una opción? La buscamos en la paleta escribiendo lo que queremos hacer: "toggle word wrap", "change language mode", "git create branch", "markdown open preview". Además, la paleta muestra junto a cada acción su atajo de teclado, así que es también la forma de ir aprendiéndolos.

### Atajos que usaremos a diario

| Acción | Windows / Linux | macOS |
|---|---|---|
| Paleta de comandos | `Ctrl + Shift + P` | `Cmd + Shift + P` |
| Abrir archivo por nombre | `Ctrl + P` | `Cmd + P` |
| Mostrar / ocultar terminal | `Ctrl + ñ` | `Ctrl + ñ` |
| Mostrar / ocultar barra lateral | `Ctrl + B` | `Cmd + B` |
| Guardar | `Ctrl + S` | `Cmd + S` |
| Buscar en el archivo / en todo el proyecto | `Ctrl + F` / `Ctrl + Shift + F` | `Cmd + F` / `Cmd + Shift + F` |
| Mover la línea arriba / abajo | `Alt + ↑` / `Alt + ↓` | `Option + ↑` / `Option + ↓` |
| Duplicar la línea | `Shift + Alt + ↓` | `Shift + Option + ↓` |
| Seleccionar la siguiente aparición de la palabra | `Ctrl + D` | `Cmd + D` |
| Cursor en varios sitios a la vez | `Alt + clic` | `Option + clic` |
| Vista previa de Markdown | `Ctrl + Shift + V` | `Cmd + Shift + V` |

Algunos atajos dependen de la distribución del teclado (comentar líneas, por ejemplo, cambia entre teclado español e inglés). Ante la duda, **la paleta de comandos muestra el atajo correcto para nuestro teclado**: buscamos "toggle line comment" y lo vemos al lado.

`Ctrl + D` y los cursores múltiples merecen una prueba. Escribimos tres veces la palabra `ventas` en un archivo, hacemos doble clic en la primera y pulsamos `Ctrl + D` dos veces: las tres quedan seleccionadas y podemos reescribirlas a la vez. Cuando tengamos que renombrar una columna en una consulta SQL larga, lo agradeceremos.

## 6. Extensiones

### Cómo funcionan

Una **extensión** es un complemento que añade capacidades a VS Code: soporte de un lenguaje, un depurador, un visor de archivos, un tema de colores. Se instalan desde el **Marketplace** de VS Code, dentro del propio editor:

1. Clic en el icono **Extensions** de la barra de actividad (o `Ctrl + Shift + X`).
2. Buscamos la extensión por nombre.
3. Comprobamos el **editor** (*publisher*) y pulsamos **Install**.

> **Las extensiones ejecutan código en nuestro ordenador.** Antes de instalar una, comprobamos que el editor es el esperado (las oficiales llevan un distintivo de verificación azul), que tiene un número razonable de descargas y buenas valoraciones. Existen extensiones maliciosas que imitan el nombre de otras populares.

### Las extensiones del curso

| Extensión | Editor | Identificador | Para qué la usaremos |
|---|---|---|---|
| **Python** | Microsoft | `ms-python.python` | Ejecutar y depurar Python (bloques 3 y 4). Instala también Pylance y Python Debugger. |
| **Jupyter** | Microsoft | `ms-toolsai.jupyter` | Abrir y ejecutar notebooks `.ipynb` dentro de VS Code. |
| **Data Wrangler** | Microsoft | `ms-toolsai.datawrangler` | Explorar y limpiar DataFrames de pandas con una interfaz visual. |
| **SQLTools** | Matheus Teixeira | `mtxr.sqltools` | Conectar a bases de datos y ejecutar SQL desde VS Code. |
| **SQLTools PostgreSQL/Cockroach Driver** | Matheus Teixeira | `mtxr.sqltools-driver-pg` | El conector de SQLTools para PostgreSQL. |
| **Rainbow CSV** | mechatroner | `mechatroner.rainbow-csv` | Colorea cada columna de un CSV y permite consultarlo. |
| **markdownlint** | David Anson | `davidanson.vscode-markdownlint` | Revisa el estilo de nuestros archivos Markdown (sesión 4). |

Opcional: **Spanish Language Pack for Visual Studio Code** (Microsoft, `ms-ceintl.vscode-language-pack-es`) traduce la interfaz al español. En esta guía nombramos los menús en inglés, que es como aparecen en la documentación oficial y en la mayoría de tutoriales; recomendamos dejar la interfaz en inglés, pero es una preferencia personal.

### Instalarlas desde la terminal

Las extensiones también se pueden instalar con el comando `code`, lo que es útil para instalar todas de una vez. Desde la terminal integrada:

```bash
code --install-extension ms-python.python
code --install-extension ms-toolsai.jupyter
code --install-extension ms-toolsai.datawrangler
code --install-extension mtxr.sqltools
code --install-extension mtxr.sqltools-driver-pg
code --install-extension mechatroner.rainbow-csv
code --install-extension davidanson.vscode-markdownlint
```

Comprobamos la lista de instaladas:

```bash
code --list-extensions
```

## 7. Configuración

### Dos formas de configurar: interfaz y JSON

Toda la configuración de VS Code se guarda en archivos de texto en formato **JSON**. Podemos cambiarla de dos maneras:

- **Interfaz de ajustes:** **File > Preferences > Settings** (`Ctrl + ,`). Un buscador con casillas y desplegables. Cómodo para explorar.
- **Archivo `settings.json`:** paleta de comandos → **Preferences: Open User Settings (JSON)**. El texto directo. Cómodo para copiar una configuración completa.

Los dos editan lo mismo: si cambiamos una casilla en la interfaz, aparece la línea correspondiente en el JSON.

### Usuario vs espacio de trabajo

- **Ajustes de usuario (*User*):** se aplican a todo lo que abramos en VS Code, en nuestro ordenador.
- **Ajustes de espacio de trabajo (*Workspace*):** se guardan en `.vscode/settings.json` dentro del proyecto y **solo** se aplican a ese proyecto. Como están en el repositorio, viajan con él a GitHub y los recibe cualquiera que lo clone.

Regla práctica: preferencias personales (tamaño de letra, tema) en usuario; reglas del proyecto que deban compartir todos, en espacio de trabajo.

### Configuración recomendada para el curso

Abrimos **Preferences: Open User Settings (JSON)** y dejamos el archivo así (si ya tenía contenido, añadimos estas líneas dentro de las llaves):

```json
{
    "editor.fontSize": 14,
    "editor.wordWrap": "on",
    "editor.renderWhitespace": "boundary",
    "editor.minimap.enabled": false,
    "files.autoSave": "afterDelay",
    "files.trimTrailingWhitespace": true,
    "files.insertFinalNewline": true,
    "git.autofetch": true,
    "[markdown]": {
        "files.trimTrailingWhitespace": false
    }
}
```

| Ajuste | Qué hace |
|---|---|
| `editor.fontSize` | Tamaño de letra del editor. Lo ajustamos a nuestra pantalla. |
| `editor.wordWrap` | Las líneas largas se ajustan a la ventana en lugar de obligarnos a hacer scroll horizontal. Muy útil en Markdown. |
| `editor.renderWhitespace` | Muestra los espacios que no son separadores simples entre palabras (dobles espacios, espacios al final). Ayuda a detectar errores invisibles. |
| `editor.minimap.enabled` | Oculta el minimapa de la derecha, que quita espacio y aporta poco al principio. |
| `files.autoSave` | Guarda automáticamente al poco de dejar de escribir. Adiós a "no había guardado". |
| `files.trimTrailingWhitespace` | Elimina espacios sobrantes al final de las líneas al guardar. |
| `files.insertFinalNewline` | Asegura que todo archivo termina con un salto de línea (una convención que Git y muchas herramientas esperan). |
| `git.autofetch` | Consulta periódicamente GitHub para avisarnos si hay cambios que no tenemos. |
| `"[markdown]"` | Excepción para Markdown: allí dos espacios al final de una línea significan salto de línea (sesión 4), así que no los borramos. |

> JSON es estricto con la sintaxis: cada línea termina en coma **excepto la última** de cada bloque, y todo va entre comillas dobles. Si VS Code subraya algo en rojo en `settings.json`, casi siempre es una coma que sobra o que falta.

### VS Code como editor de Git

En la sesión 2 dejamos Notepad (o Nano) como editor de Git. Ahora que tenemos VS Code, lo configuramos para que Git lo use cuando necesite que escribamos algo (por ejemplo, un mensaje de commit si olvidamos `-m`):

```bash
git config --global core.editor "code --wait"
```

`--wait` hace que Git espere a que cerremos la pestaña antes de continuar.

## 8. Nuestro portfolio en VS Code paso a paso

Vamos a añadir al portfolio un archivo de **extensiones recomendadas**, esta vez haciendo el flujo de Git con el panel visual de VS Code en lugar de comandos.

### Paso 1: crear una rama desde la terminal integrada

Abrimos la terminal integrada (`Ctrl + ñ`) y comprobamos que partimos de `main` actualizado:

```bash
git switch main
git pull
git switch -c configurar-vscode
```

Fijémonos en la **barra de estado**, abajo a la izquierda: ahora muestra `configurar-vscode`. Haciendo clic ahí también se pueden crear y cambiar ramas.

### Paso 2: crear el archivo de extensiones recomendadas

En el **Explorer**, pasamos el ratón sobre el nombre del proyecto y pulsamos el icono **New Folder**; la llamamos `.vscode`. Sobre ella, **New File**: `extensions.json`. Escribimos:

```json
{
    "recommendations": [
        "ms-python.python",
        "ms-toolsai.jupyter",
        "ms-toolsai.datawrangler",
        "mtxr.sqltools",
        "mtxr.sqltools-driver-pg",
        "mechatroner.rainbow-csv",
        "davidanson.vscode-markdownlint"
    ]
}
```

Este archivo no instala nada por sí mismo: cuando alguien abra el repositorio en VS Code, el editor le **sugerirá** instalar estas extensiones. Es la forma estándar de documentar "este proyecto se trabaja con estas herramientas".

### Paso 3: revisar los cambios en Source Control

Clic en el icono **Source Control** de la barra de actividad. VS Code muestra una lista de **Changes** con `extensions.json` marcado con una `U` (*untracked*). Es exactamente lo que nos diría `git status`.

Clic sobre el archivo: se abre una vista de diferencias con lo añadido en verde. Es lo mismo que veíamos en la pestaña *Files changed* del pull request en GitHub, pero en local y antes de hacer commit.

### Paso 4: stage y commit

- Pasamos el ratón sobre el archivo y pulsamos el **`+`** (*Stage Changes*). El archivo pasa a la sección **Staged Changes**: es nuestro `git add`.
- En la caja de texto superior escribimos el mensaje: `Añadir extensiones recomendadas de VS Code`.
- Pulsamos **Commit**: es nuestro `git commit -m`.

### Paso 5: publicar la rama y abrir el pull request

Tras el commit, el botón azul cambia a **Publish Branch**. Lo pulsamos: equivale a `git push -u origin configurar-vscode`.

Vamos a GitHub y, como en la sesión anterior, **Compare & pull request** → descripción breve → **Create pull request** → **Merge pull request** → **Delete branch**.

### Paso 6: volver a `main` y sincronizar

En VS Code, clic en el nombre de la rama de la barra de estado → elegimos `main`. Después, en Source Control, el botón **Sync Changes** (o el icono de flechas circulares de la barra de estado) hace `git pull` y `git push` a la vez. Nuestro `main` local ya tiene el `.vscode/extensions.json`.

Podemos borrar la rama local desde la paleta: **Git: Delete Branch...** → `configurar-vscode`.

## 9. Lo que VS Code ha hecho por debajo

El panel de Source Control no tiene un Git propio: **ejecuta los mismos comandos de Git** que escribimos en la sesión 2. Podemos verlo: **View > Output** y, en el desplegable de la derecha del panel, elegimos **Git**. Aparece el registro de cada comando que VS Code ha lanzado en nuestro nombre. Entre muchas líneas técnicas, reconoceremos algo así (simplificado):

```
> git add -A -- .vscode/extensions.json
> git commit --quiet --allow-empty-message --file -
> git push -u origin configurar-vscode
```

Esto tiene una consecuencia importante: **la terminal y el panel visual son intercambiables**. Podemos hacer commit con uno y push con otro, y ambos verán siempre el mismo estado, porque el estado vive en la carpeta `.git`, no en VS Code.

Algo parecido ocurre con la configuración: nuestras preferencias de usuario viven en un archivo `settings.json` en nuestra carpeta personal (`%APPDATA%\Code\User\` en Windows, `~/Library/Application Support/Code/User/` en macOS), y las del proyecto en `.vscode/` dentro del repositorio. Todo es texto plano; nada está escondido en un registro binario.

Y las extensiones son, en su mayoría, programas escritos en JavaScript que VS Code ejecuta en un proceso separado llamado *Extension Host*. Si una extensión falla, el editor sigue funcionando.

## 10. Errores comunes y troubleshooting

**1. "code no se reconoce como comando."** En Windows, no marcamos *Add to PATH* en el instalador, o la terminal estaba abierta desde antes de instalar. Abrimos una terminal nueva; si persiste, reinstalamos marcando la opción. En macOS, falta el paso **Shell Command: Install 'code' command in PATH**.

**2. "Source Control dice que no hay repositorio."** Hemos abierto un archivo suelto, o una carpeta superior o interior al repositorio. VS Code detecta el repositorio por la carpeta `.git`: abrimos exactamente la carpeta `mi-portfolio-data-analytics` con **File > Open Folder** o con `code .` desde ella.

**3. "VS Code está en modo restringido (*Restricted Mode*)."** No confiamos en la carpeta al abrirla y algunas extensiones están desactivadas. Clic en **Restricted Mode** en la barra de estado → **Trust**.

**4. "settings.json tiene líneas rojas."** Error de sintaxis JSON: una coma que falta entre dos ajustes, una coma sobrante tras el último, o comillas tipográficas (`“ ”`) en lugar de rectas (`" "`) por haber copiado de un documento. Pasamos el ratón sobre el subrayado para ver el error.

**5. "El atajo de la terminal no hace nada."** Depende del teclado. Usamos **View > Terminal** o buscamos "toggle terminal" en la paleta de comandos para ver el atajo correcto en nuestro teclado.

**6. "La barra de estado muestra CRLF y un compañero ve LF."** Son los finales de línea de Windows y Unix. Git los normaliza al hacer commit, así que no hay que hacer nada. Si un archivo concreto lo necesita, se puede cambiar haciendo clic sobre `CRLF` en la barra de estado.

**7. "He hecho commit desde VS Code y no aparece en GitHub."** Un commit es local. Falta el push: botón **Sync Changes** o **Publish Branch** en Source Control, o `git push` en la terminal.

## 12. Para profundizar

### Perfiles y sincronización de ajustes

- **Settings Sync:** con **Backup and Sync Settings** (icono de la cuenta, abajo a la izquierda) VS Code guarda nuestros ajustes, extensiones y atajos en la nube con la cuenta de GitHub o Microsoft, y los restaura en otro ordenador.
- **Profiles:** permiten tener configuraciones separadas (por ejemplo, un perfil "Data Analytics" con sus extensiones y otro "Clases" con letra grande para proyectar). Paleta → **Profiles: Create Profile**.

### Snippets

Un *snippet* es una plantilla de código que se inserta escribiendo un atajo. Paleta → **Snippets: Configure Snippets** → `sql.json`. Por ejemplo, para insertar el esqueleto de una consulta escribiendo `sel`:

```json
{
    "Consulta básica": {
        "prefix": "sel",
        "body": [
            "SELECT ${1:columnas}",
            "FROM ${2:tabla}",
            "WHERE ${3:condicion};"
        ]
    }
}
```

### Otras extensiones que aparecen en entornos profesionales

- **GitLens** (`eamodio.gitlens`): muestra quién y cuándo modificó cada línea, e historial avanzado.
- **Remote - SSH** y **WSL**: editar archivos en un servidor remoto o en Linux dentro de Windows como si estuvieran en local.
- **Dev Containers**: trabajar dentro de un contenedor Docker con un entorno reproducible.
- **Asistentes de IA** para programar, integrados en el editor. Los veremos con perspectiva crítica en la sesión 4.3.1.

### Depurar código

El icono **Run and Debug** permite ejecutar Python paso a paso, inspeccionando las variables en cada línea con *breakpoints*. Es la mejor forma de entender por qué un script no hace lo que esperamos, y lo usaremos en el bloque 3.
